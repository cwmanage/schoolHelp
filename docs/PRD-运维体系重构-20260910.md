## 2. 用户故事（带验收标准）

### US-1 运维者 / root —— 服务自启
> 作为服务器运维者（root），我希望**服务器重启后 4 个后端服务自动拉起**，这样半夜重启或宕机后不用我手动 `java -jar`。

**验收标准**
1. `systemctl is-enabled schoolhelp-gateway schoolhelp-user schoolhelp-course schoolhelp-biz` 全部输出 `enabled`。
2. 执行 `reboot` 后**不执行任何手工命令**，`ss -ltnp | grep -E ':8080|:8101|:8102|:8103'` 能看到 4 个端口均在监听。
3. 断开当前 SSH 会话（或杀掉父会话）后，`systemctl is-active schoolhelp-*` 仍为 `active`，服务不随会话消失。

### US-2 运维者 / root —— 一键重启
> 作为运维者，我希望**一条命令重启后端 / 前端**，不用记 systemd 与 Nginx 的细节。

**验收标准**
1. root 登录后可直接执行重启后端脚本，脚本内部完成「jar 存在性校验 → 重启 4 个服务 → 等待端口就绪 → 打印各服务状态 → 冒烟测试网关登录接口」；冒烟返回 HTTP 200 表示「网关 + user + DB」全通。
2. 前端重启脚本执行后 `nginx -t` 通过、Nginx reload 成功，并打印 `:80`、`:8081` 的本机 HTTP 状态码（均应为 200）。
3. 脚本无需 `cd`、无需手工 `export` 环境变量即可跑通（root 登录态直接可用）。

### US-3 运维者 / root —— 一键拉取打包部署
> 作为运维者，我希望**一条命令从 GitHub 拉最新代码 → 打包前后端 → 铺到启动目录 → 重启**，实现「代码 push 后服务器一键上线」。

**验收标准**
1. 脚本执行后打印当前提交哈希，与 `origin/master` 一致。
2. 后端 4 个 jar 被重新生成并落到 `/opt/schoolhelp/<服务>/` 各自目录下（时间戳刷新）。
3. 前端两端 `dist` 被铺到 `/var/www/schoolhelp/pc/` 与 `/var/www/schoolhelp/m/`。
4. 执行完成后自动触发重启流程，`admin/admin123` 登录接口返回 200。
5. 解决用户疑问：脚本内（或配套说明中）明确回答「**需要上传哪些依赖包、放在什么目录**」。

### US-4 运维者 / root —— 一键更新前端
> 作为运维者，我希望**只改前端时不必重打后端**，用一条更快的命令只更新前端。

**验收标准**
1. 脚本支持只更新移动端 / 只更新 PC 端 / 两端都更三种粒度。
2. 仅改前端场景下**不重新执行 Maven 打包**，耗时明显短于全量部署。
3. 执行后 `/var/www/schoolhelp/{pc,m}/index.html` 时间戳刷新，站点 `:80`/`:8081` 返回 200。

### US-5 开发者（Windows 本地）—— 本地开发不被破坏
> 作为本机 Windows 开发者，我希望**改完上传目录 / 日志配置后，IDEA 跑后端和 `npm run dev` 跑前端仍然正常**。

**验收标准**
1. 本地（Windows）`application.yml` 不依赖服务器环境变量即可启动；`start-all.ps1` 一键启动 4 个服务后端口全部就绪。
2. 前端 `npm run dev` 正常（移动端 5173 / PC 端 5174），dev proxy 指向 `127.0.0.1:8080`，`/api` 代理通。
3. 本地访问 `localhost:5173` / `localhost:5174` **不触发设备跳转**（UA 脚本对 `localhost/127.0.0.1/0.0.0.0` 已短路）。
4. 本地头像 / 课件上传仍可正常保存与访问。

### US-6 管理员 —— 班长审批
> 作为管理员，我希望**班长注册后必须经我审批通过才能登录**，这样避免有人冒充班长自助注册。

**验收标准**
1. 注册一个班长角色账号 → 立即登录返回 403，提示「账号待管理员审批，请耐心等待」。
2. 管理员可查询到待审批班长列表；执行「通过」后该账号登录成功并签发 JWT。
3. 执行「驳回」时**必须填写原因**（不填则被拒绝），驳回后该账号登录返回 403「注册申请未通过，请联系管理员」。
4. 普通同学（角色 0）注册后**无需审批**即可直接登录，不受影响。
5. 存量用户不被误挡（v3 回填为「已通过」）。

### US-7 学生用户 —— 设备自动分流
> 作为学生用户，我希望**用手机打开就自动进手机版、用电脑打开就自动进电脑版**，不用自己找地址。

**验收标准**
1. 电脑浏览器访问 `http://47.83.169.101/` 停留在 PC 版；访问 `http://47.83.169.101:8081/` 自动跳回 `:80`（PC 版）。
2. 手机浏览器访问 `:80` 自动跳到 `:8081`（手机版）；访问 `:8081` 正常停留。
3. 线上 `http://47.83.169.101/` 返回的 `index.html` **含**分流脚本且体积为新构建（约 2043 字节）；`:8081` 同理含 `force_mobile`。
4. 加 `?pc=1` / `?mobile=1` 可强制停留在对应端，且在同一次会话内记得该选择。

## 3. 需求池（含优先级与理由）

> 优先级定义：**P0 = 本轮必须完成**（不做则上线不合格 / 有安全隐患 / 无法验收）；**P1 = 本轮应完成**（显著提升可运维性，可小幅顺延）；**P2 = 可延后**。

| 编号 | 需求 | 优先级 | 优先级理由 |
|------|------|--------|------------|
| **N1** | 服务器目录重构：每 jar 独立目录 `/opt/schoolhelp/<服务>/`（无 `app` 中间层） | **P0** | ① 是要求①②③脚本「产物落到哪」的**共同前提**，先定目录才有稳定脚本；② 当前 jar 全堆在根目录、无隔离，是本次重构的核心；③ 与 ① 的 systemd `WorkingDirectory`、③ 的部署路径强耦合，必须在脚本落地前定稿 |
| **N2** | 日志分级：`app.log`（INFO+ 全量）+ `error.log`（仅 ERROR），按天滚动、保留 N 天 | **P1** | 属于**可观测性 / 可运维性**增强，不阻塞功能上线，故不列 P0；但线上排障强依赖它（当前是 shell 重定向的单文件日志，无级别区分），且 B2 修复后分级才真正生效，故列 P1 而非 P2。**保留天数：建议 14 天**，做成可配置项（P1）——小规模校园应用日志量不大，14 天足够回溯一次线上问题的排查窗口，同时避免占满磁盘 |
| **要求①** | root 直跑的「一键重启后端」「一键重启前端」脚本 | **P0** | 用户首要诉求，且直击**当前最大隐患**：后端是裸 `java -jar`、父进程是 SSH 会话，会话一断整套可能消失、且无自启机制。不解决则线上随时可能整体宕机，必须 P0 |
| **要求②** | 安装 git + 「一键拉取代码并打包（含前后端）」脚本，产物落到启动目录；并回答依赖包问题 | **P0** | 是「服务器自主上线」的核心链路，也是用户明确点名要的能力；与 N1 目录重构一体交付 |
| **要求③** | 「一键更新前端包」脚本（前后端更新方式不同） | **P1** | 有明确价值（只改前端时省去 Maven 全量打包时间），但**可用要求② 的全量脚本替代**，独立性与紧迫性次之，故 P1 |
| **要求④** | 班长注册需管理员审批通过后方可登录（**代码已完成，仅差线上落地**） | **P0** | **功能代码 + v3 迁移脚本均已完成并通过提交**（`231383e`），线上运行的是旧 jar，属于「成果已就绪、只差上线」；且是用户明确的功能诉求，本轮不落地等于白做，必须 P0 |
| **要求⑥** | 设备自动检测分流，非 PC 端展示手机端（**代码已完成，仅差线上落地**） | **P0** | 同上：两套 `index.html` 的 UA 分流脚本**代码已完成并提交**，但线上仍是 19:51 旧构建（无分流脚本），功能实际未生效；属「只差重新构建+发布前端」，成本低、收益明确，必须 P0 |
| **B1** | 上传目录硬编码 Windows 路径 `D:/homework/...` 在 Linux 上生成畸形目录 | **P0** | **会带病上线**：Linux 下会被解析为 `/opt/schoolhelp/D:/homework/...` 之类的畸形目录树，头像/课件写入错误位置、可能上传后无法访问；且需改为**可由环境变量/配置覆盖**以同时满足服务器与本地开发。属上线前必须修的正确性问题 |
| **B2** | MyBatis `log-impl: StdOutImpl` 绕过日志框架直接打印全部 SQL | **P0** | ① **安全**：走 `System.out`，不受日志级别控制，生产环境会把**带参数的 SQL 全量刷进日志，存在敏感数据泄露风险**；② **使 N2 失效**：级别调到 WARN 也压不住 SQL 输出，不改则 N2 的「日志分级」形同虚设。故 B2 为 N2 的**生效前提**，列 P0 |

### 优先级小结
- **P0（7 项）**：N1、要求①、要求②、要求④、要求⑥、B1、B2
- **P1（3 项）**：N2（含「保留天数可配置」子项）、要求③
- **P2（0 项）**

> 备注：`deploy/` 下已有 6 个脚本 + `deploy/README.md`，它们已覆盖要求①②③的主体，但**内部目录约定为 `/opt/schoolhelp/app/`**，与 N1 冲突，且 `init-server.sh` 的 systemd 单元当前指向 `$APP=$BASE/app`。因此要求①②③ 本轮的实际工作包含「按 N1 校正路径 + 在真实服务器上验证可跑通」，而非从零新写。

## 4. 依赖包方案（回答用户「需要上传哪些依赖包、放什么目录」）

### 4.1 结论（联网方案，推荐）

**服务器可正常出网时，不需要手工上传任何依赖包。** 只需 `apt` 装好工具链，Maven / npm 依赖让服务器自己拉取：

| 依赖类型 | 放置目录 | 大小量级 | 获取方式 | 是否需上传 |
|----------|----------|----------|----------|------------|
| 系统工具链 git / maven / JDK17 / Node18 | 系统路径（apt / NodeSource） | — | `apt install`、NodeSource 脚本 | 否，`init-server.sh` 自动安装 |
| Maven 依赖（后端） | `~/.m2/repository`（root 下即 `/root/.m2/repository`） | 首次约 **200–400MB** | `mvn` 自动下载 | **否** |
| npm 依赖（前端） | `schoolhelp-web/node_modules`、`schoolhelp-web-pc/node_modules` | 各约 **110–150MB** | `npm install` 自动下载 | **否** |
| 数据库驱动等运行时依赖 | 已打进胖 jar | — | 随 jar 分发 | 否（fat jar 自带） |
| Nacos / MySQL | 已在服务器本机运行 | — | 不属于本轮范围 | 否 |

**加速建议**：Maven 配阿里云镜像（`https://maven.aliyun.com/repository/public`），npm 配淘宝镜像（`https://registry.npmmirror.com`）——现有 `pull-build-deploy.sh` / `update-frontend.sh` 已内置这两个镜像地址，沿用即可。

> ⚠️ `~/.m2/repository` 与 `node_modules/` **都不要上传、不要提交 git**（`.gitignore` 已忽略 `node_modules/`；`~/.m2` 在用户主目录天然不入库）。

### 4.2 备选（离线部署，仅当服务器不能出网）

按 N1 的目录约定，离线时需从**本地（Windows）**上传以下产物：

| 上传内容 | 本地来源 | 服务器目标目录 |
|----------|----------|----------------|
| 4 个后端 jar | `schoolhelp-{gateway,user,course,biz}/target/schoolhelp-*.jar` | `/opt/schoolhelp/gateway/`、`/opt/schoolhelp/user/`、`/opt/schoolhelp/course/`、`/opt/schoolhelp/biz/` |
| PC 端构建产物 | `schoolhelp-web-pc/dist/` | `/var/www/schoolhelp/pc/` |
| 移动端构建产物 | `schoolhelp-web/dist/` | `/var/www/schoolhelp/m/` |
| SQL 增量脚本 | `sql/v3_user_approve_migration.sql` | 手动导入数据库（服务器本地执行） |

若必须**在服务器上**离线构建（而非上传产物），还需额外离线准备：
- 本地 `~/.m2/repository` 整体打包上传（配合 `mvn -o` 离线模式）；

> 离线方案成本显著高于联网方案（传输量数百 MB、易踩架构/版本不一致问题），**仅在服务器确无外网出口时采用**。
